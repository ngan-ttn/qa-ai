# Artifact Quality Criteria

- Evaluation ID: `EVAL-CRITERIA-001`

- Status: `Approved`
- Purpose: Define the common quality dimensions used to evaluate QA artifacts generated by QA-AI Skills and Workflows.

---

## Purpose

This document defines the common quality criteria used to evaluate QA artifacts produced by the QA-AI framework.

The criteria establish what should be assessed when reviewing generated outputs such as:

- Requirement Analysis
- Business Rules
- Risk Analysis
- Test Scenarios
- Test Cases
- Regression Analysis

The criteria are intentionally separated from scoring and rubric definitions.

This document defines **what quality dimensions are evaluated**.

It does not define:

- Numeric scores
- Pass/fail thresholds
- Criterion weights
- Artifact-specific prompts
- Skill execution behavior
- Workflow orchestration

Those responsibilities belong to the applicable rubric, scoring, Skill, or Workflow definitions.

---

## Evaluation Principles

QA-AI evaluation should follow the following principles.

### Source-Grounded

Generated artifacts must remain grounded in the supplied requirement and authoritative supporting inputs.

Evaluation must penalize invented business behavior, unsupported dependencies, and unjustified assumptions.

### Artifact-Aware

Different QA artifacts serve different purposes.

A Requirement Analysis should not be evaluated as if it were a Test Case artifact, and a Regression Analysis should not be expected to contain detailed executable steps unless its contract requires them.

### Traceable

Important generated content should be traceable to its originating requirement, rule, risk, scenario, or other relevant source.

### Complete but Controlled

Generated artifacts should cover all relevant source behavior without expanding unnecessarily beyond the defined scope.

### Non-Duplicative

Coverage should be comprehensive without creating unnecessary repeated artifacts that verify the same objective.

### Reviewable

A human reviewer should be able to understand:

- What was derived
- Why it was derived
- What source supports it
- What remains unknown

### Consistent

Terminology, identifiers, business concepts, and traceability relationships should remain consistent across related artifacts.

## Core Quality Criteria

The following criteria apply broadly across QA-AI generated artifacts.

---

## C01 — Requirement Fidelity

### Definition

Measures whether the generated artifact correctly represents the source requirement without altering its intended behavior.

### Evaluation Focus

Evaluate whether the artifact:

- Preserves defined business behavior.
- Preserves thresholds, limits, durations, states, roles, and conditions.
- Avoids contradicting the source.
- Avoids replacing source terminology with materially different concepts.
- Distinguishes source-defined behavior from interpretation.

### Positive Indicators

- Exact business constraints are preserved.
- Source scope is respected.
- Derived content is compatible with acceptance criteria.
- No unsupported behavior is presented as confirmed.

### Negative Indicators

- Thresholds or values are changed.
- Business logic is invented.
- Requirement behavior is omitted or distorted.
- Out-of-scope functionality is treated as required behavior.

---

## C02 — Correctness

### Definition

Measures whether the artifact's derived QA content is logically correct and internally valid.

### Evaluation Focus

Evaluate whether:

- Derived rules are logically consistent.
- Test expectations match the requirement.
- State transitions are valid.
- Boundary behavior is interpreted correctly.
- Risk reasoning reflects plausible failure modes.
- Regression impact is supported by the available evidence.

### Positive Indicators

- Expected results are measurable and logically valid.
- Rule relationships do not contradict one another.
- State and sequence behavior remain coherent.
- Derived conclusions follow from the source.

### Negative Indicators

- Internal contradictions.
- Impossible state transitions.
- Incorrect expected results.
- Invalid dependency conclusions.
- Conflicting rule interpretations.

---

## C03 — Completeness

### Definition

Measures whether all relevant source-defined behavior has been represented in the artifact.

### Evaluation Focus

Evaluate coverage of:

- Acceptance criteria
- Business rules
- States
- Boundaries
- Valid and invalid flows
- Roles
- Relevant data conditions
- Requirement-defined dependencies

Completeness must be assessed relative to the artifact type.

### Positive Indicators

- No source acceptance criterion is unintentionally omitted.
- Critical states and boundaries are represented.
- Relevant negative behavior is included where applicable.

### Negative Indicators

- Missing source behavior.
- Missing critical boundary.
- Missing role-specific condition.
- Missing negative or failure path explicitly defined by the requirement.

---

## C04 — Scope Control

### Definition

Measures whether the artifact stays within the intended responsibility of its artifact type and source scope.

### Evaluation Focus

Evaluate whether the artifact:

- Avoids unrelated feature expansion.
- Avoids implementation assumptions.
- Separates confirmed behavior from potential impact.
- Keeps out-of-scope behavior clearly identified.
- Does not perform downstream QA responsibilities unnecessarily.

### Positive Indicators

- Requirement Analysis analyzes but does not prematurely generate full Test Cases.
- Risk Analysis identifies risk without inventing implementation details.
- Regression Analysis distinguishes confirmed and potential impact.
- Test Cases stay executable and focused.

### Negative Indicators

- Full specification invented from limited requirements.
- Architecture or API behavior assumed without evidence.
- Artifact contains unrelated QA outputs.
- Out-of-scope behavior treated as mandatory.

---

## C05 — Assumption Control

### Definition

Measures how well the artifact identifies and manages missing information.

### Evaluation Focus

Evaluate whether:

- Unsupported assumptions are avoided.
- Ambiguities are surfaced.
- Unknown behavior remains explicitly unknown.
- Clarification-dependent content is separated from confirmed content.
- Implementation choices are not converted into business rules.

### Positive Indicators

- "Not specified" behavior remains unconfirmed.
- Clarification questions are relevant.
- Potential impacts are labeled appropriately.

### Negative Indicators

- Missing behavior silently invented.
- Assumptions presented as facts.
- Undefined technical mechanisms treated as required implementation.

---

## C06 — Traceability

### Definition

Measures whether generated content can be connected back to its source behavior and related QA artifacts.

### Evaluation Focus

Evaluate whether:

- Requirements map to derived rules.
- Rules map to scenarios.
- Scenarios map to test cases.
- Risks map to relevant coverage.
- Regression areas map to requirement behavior.
- Identifiers remain consistent.

### Positive Indicators

- Stable IDs are used consistently.
- Acceptance criteria have downstream coverage.
- No orphan confirmed artifact exists.

### Negative Indicators

- Broken references.
- Untraceable test cases.
- Rule IDs change unexpectedly.
- Scenario or test case has no supported source.

---

## C07 — Clarity

### Definition

Measures whether the artifact communicates QA intent precisely and understandably.

### Evaluation Focus

Evaluate:

- Terminology consistency.
- Statement precision.
- Section organization.
- Readability.
- Ambiguity introduced by wording.
- Appropriate level of detail.

### Positive Indicators

- Clear objectives.
- Explicit conditions.
- Concise explanations.
- Consistent domain terminology.

### Negative Indicators

- Vague wording.
- Unclear expected results.
- Ambiguous references.
- Excessive verbosity that hides the actual rule or test intent.

---

## C08 — Testability

### Definition

Measures whether QA-relevant outputs are concrete enough to support verification.

### Evaluation Focus

For applicable artifacts, evaluate whether behavior can be verified through:

- Defined conditions
- Observable outcomes
- Explicit boundaries
- Measurable state changes
- Deterministic expected behavior

### Positive Indicators

- Expected result can be verified.
- Preconditions are understandable.
- Boundaries are identifiable.
- Required behavior is objectively observable.

### Negative Indicators

- "Works correctly."
- "Looks good."
- "Should behave normally."
- Unmeasurable or subjective outcomes.

This criterion may have lower relevance for non-executable artifacts such as high-level Requirement Analysis.

---

## C09 — Coverage Efficiency

### Definition

Measures whether the artifact achieves sufficient coverage without unnecessary duplication.

### Evaluation Focus

Evaluate:

- Duplicate rules
- Duplicate scenarios
- Duplicate test cases
- Redundant risk entries
- Meaningful separation of objectives

### Positive Indicators

- Each item has a distinct primary purpose.
- Overlapping behavior exists only where required by different objectives.
- Coverage remains compact and understandable.

### Negative Indicators

- Multiple cases verify the same primary objective.
- Rule lists split one simple rule unnecessarily.
- Repeated scenarios add no meaningful coverage.

---

## C10 — Boundary and State Coverage

### Definition

Measures whether relevant boundaries, states, transitions, and sequence-dependent behavior are represented correctly.

### Evaluation Focus

Where applicable, evaluate:

- Minimum and maximum values
- Threshold boundaries
- Before/at/after conditions
- State transitions
- Reset behavior
- Repeated lifecycle behavior
- Sequence-dependent rules

### Positive Indicators

- Both sides of critical threshold covered.
- State transitions explicitly identified.
- Reset starts a new sequence where required.

### Negative Indicators

- Only happy-path values tested.
- Exact threshold omitted.
- State change inferred incorrectly.
- Sequential dependencies ignored.

---

## C11 — Risk Awareness

### Definition

Measures whether business-critical and failure-prone areas receive appropriate attention.

### Evaluation Focus

Evaluate whether:

- Critical behavior receives sufficient QA focus.
- Security-sensitive or data-integrity-sensitive behavior is recognized.
- High-impact failure modes are represented.
- Risk priority is reasonable.

### Positive Indicators

- Critical threshold receives high priority.
- Data isolation risk is recognized.
- State corruption or business-impact risks are captured.

### Negative Indicators

- All risks assigned the same reasoning without justification.
- Critical behavior treated as low priority.
- Important failure modes ignored.

---

## C12 — Internal Consistency

### Definition

Measures consistency within an artifact and across related QA artifacts.

### Evaluation Focus

Evaluate whether:

- Terms retain the same meaning.
- Values remain consistent.
- IDs remain stable.
- Rules do not conflict.
- Scenario and test-case expectations agree.
- Regression analysis matches confirmed source behavior.

### Positive Indicators

- Same lock duration used across all artifacts.
- Same rule identifiers referenced consistently.
- Scenario and test-case expected behavior match.

### Negative Indicators

- Different values for the same rule.
- Conflicting states.
- Broken artifact relationships.
- Duplicate IDs with different meanings.

## Critical Quality Failures

Certain failures should be treated as more severe than ordinary quality weaknesses.

Examples include:

### Source Contradiction

Generated behavior directly contradicts an explicit requirement.

### Fabricated Business Rule

The artifact presents unsupported behavior as confirmed business logic.

### Critical Coverage Omission

A business-critical source acceptance criterion has no meaningful coverage.

### Incorrect Expected Result

A test case expects behavior inconsistent with the requirement.

### Broken Traceability

A confirmed downstream artifact cannot be connected to its source behavior.

### Scope Leakage

The artifact asserts architecture, API, database, role, or dependency behavior that is not supported by the source.

### Internal Conflict

Two parts of the same artifact define incompatible behavior.

Rubric and scoring definitions may apply stronger penalties or caps when critical failures are present.

---

## Evaluation Evidence

Evaluation decisions should be based on observable evidence from:

1. Source requirement datasets.
2. Authoritative fixtures explicitly attached to the dataset.
3. Generated artifact content.
4. Related upstream QA artifacts where applicable.
5. Defined artifact contracts.
6. Evaluation rubrics and scoring rules.

Evaluators must not introduce external assumptions merely to justify or penalize generated behavior.

---

## Evaluation Boundaries

The criteria do not evaluate:

- Writing style preference alone.
- Exact sentence matching with golden outputs.
- Model identity.
- Token usage unless separately defined.
- Platform-specific formatting differences that do not affect artifact quality.
- Implementation behavior not represented in the evaluation inputs.

Golden outputs are reference interpretations, not byte-for-byte expected responses.

A generated artifact may differ from the golden output and still satisfy the evaluation criteria.

---

## Relationship to Rubrics and Scoring

The evaluation layers are separated as follows:

`Criteria → Rubrics → Scoring`

### Criteria

Define what quality dimensions are evaluated.

This document belongs to this layer.

### Rubrics

Define observable quality levels for each criterion.

### Scoring

Defines numeric values, weights, thresholds, aggregation, and result interpretation.

This separation allows quality definitions to evolve without rewriting source datasets or golden reference artifacts.

---

## Evaluation Usage

The criteria may be used for:

- Manual QA artifact review
- AI-assisted evaluation
- Automated evaluation pipelines
- Cross-platform comparison
- Baseline benchmarking
- Framework regression detection
- Skill-level evaluation
- Workflow-level evaluation

The applicable rubric and scoring model should identify which criteria are active for a specific evaluation.
