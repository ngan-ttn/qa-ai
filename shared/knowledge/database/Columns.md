# Columns

> Version: 1.0.0  
> Status: Approved  
> Last Updated: 2026-08-13

## Overview

A **column** defines a named attribute in a relational table. Its definition commonly includes a data type and may include nullability, default values, generated expressions, collation, constraints, or identity behavior.

## Purpose

This article helps QA validate field-to-database mapping, boundary behavior, null/default semantics, type conversion, precision, and schema-change impact.

## Core Concepts

### Data Type
The type controls the class of values that can be stored and affects comparison, arithmetic, ordering, serialization, and storage.

### Nullability
`NULL` represents an unknown or absent value under SQL semantics. It is not automatically equivalent to empty string, zero, false, or missing JSON property.

### Default
A database default can provide a value when an insert omits a column, but application code may override or bypass it.

### Generated / Identity Column
Some values are computed or generated by the DBMS rather than supplied directly.

### Precision and Scale
Numeric types may restrict digits and decimal places. Timestamp and string types can also have precision or length limits.

### Collation and Comparison
Text comparison may depend on case, accent, locale, or collation settings.

## How It Works

When a value is inserted or updated, the DBMS interprets it according to the column definition, performs conversions where supported, evaluates defaults or generated values, applies constraints, and either accepts or rejects the resulting row.

## When to Use

Use column knowledge for validation rules, boundary testing, import/export, schema migration, type mapping, null handling, date/time verification, monetary precision, and API-to-database reconciliation.

## When Not to Use

Do not assume application validation exactly matches database type rules. Do not infer business meaning from data type alone.

## Advantages

Column definitions provide concrete evidence for storage boundaries, requiredness, precision, and structural integrity.

## Limitations

DBMS products differ in implicit conversion, maximum sizes, collations, date ranges, timezone handling, and treatment of empty strings. Application frameworks may transform values before persistence.

## Examples

### Decimal Precision
A price column defined as a fixed-precision decimal can preserve exact monetary values better than a floating type, but the allowed precision must still be confirmed from the schema.

### Nullable Field
An optional middle name can be stored as `NULL`, while an empty string may be a distinct stored value. QA should validate the project's chosen convention rather than treating them as identical.

### Timestamp Mapping
An application sends an offset timestamp but the database stores UTC. QA verifies the conversion contract rather than comparing display strings directly.

## Best Practices

- Check data type, length, precision, scale, nullability, and default together.
- Validate min/max and overflow behavior for bounded types.
- Test Unicode and collation-sensitive text where relevant.
- Distinguish omitted input from explicit null.
- Confirm timezone and timestamp normalization.
- Review schema changes for truncation or conversion risk.
