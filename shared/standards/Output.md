# Output Standard

## Purpose

This document defines the standards for AI-generated outputs across the repository.

The objective is to ensure that outputs are consistent, accurate, reusable, and suitable for direct use with minimal manual modification.

---

## Scope

This standard applies to outputs generated by AI for:

* Documentation
* Templates
* Checklists
* Prompt responses
* Knowledge summaries
* Requirement analysis
* Test scenarios
* Test cases
* Bug reports
* Workflow artifacts

---

## Output Principles

Every output SHOULD be:

* **Accurate** — Correct and factually consistent.
* **Complete** — Covers all requested information.
* **Clear** — Easy to understand and follow.
* **Consistent** — Follows repository standards.
* **Actionable** — Ready for immediate use whenever possible.

---

## General Requirements

AI outputs MUST:

* Follow the requested format.
* Use professional English unless otherwise specified.
* Avoid unnecessary explanations.
* Maintain consistent terminology.
* Preserve technical accuracy.

AI outputs SHOULD:

* Be concise.
* Be logically organized.
* Minimize repetition.
* Prioritize readability.

---

## Output Structure

Unless otherwise requested, outputs SHOULD follow this structure:

1. Title (if applicable)
2. Main content
3. Supporting examples (optional)

Additional sections MAY be included when they improve clarity.

---

## Formatting

Outputs SHOULD follow the repository documentation standards.

Use:

* Headings for major sections.
* Lists for grouped information.
* Tables for structured data.
* Code blocks for examples, commands, or configurations.

Avoid excessive formatting that does not improve readability.

---

## Completeness

An output SHOULD satisfy the original request without requiring unnecessary follow-up.

When information is unavailable or assumptions are required, the output SHOULD clearly indicate them.

---

## Consistency

Outputs MUST:

* Follow repository terminology.
* Use consistent naming conventions.
* Align with related repository standards.
* Avoid contradictory statements.

---

## Reusability

Outputs SHOULD be written so they can be:

* Copied directly into repository documents.
* Reused as templates.
* Extended without major restructuring.

Avoid content that is overly specific unless explicitly requested.

---

## Examples

Examples SHOULD:

* Demonstrate the expected format.
* Be concise.
* Reflect repository conventions.

Examples SHOULD NOT replace the actual requested output.

---

## Error Handling

If the requested information is incomplete or ambiguous, the output SHOULD:

* Clearly identify missing information.
* Avoid unsupported assumptions.
* Continue only when reasonable assumptions can be made.

If assumptions are made, they SHOULD be explicitly stated.

---

## Quality Checklist

Before considering an output complete, verify that it:

* Follows the requested format.
* Covers all requested content.
* Uses consistent terminology.
* Contains no unnecessary repetition.
* Is grammatically correct.
* Can be reused with minimal modification.

---

## Best Practices

* Prioritize usefulness over verbosity.
* Prefer direct and unambiguous language.
* Produce outputs that require minimal post-editing.
* Keep formatting consistent across similar artifacts.
* Generate outputs that are immediately ready for review or publication.
