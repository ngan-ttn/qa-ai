# Output Standard

## Purpose

This document defines the standards for AI-generated outputs across the repository.

The objective is to ensure that outputs are consistent, accurate, reusable, reviewable, and suitable for direct use with minimal manual modification.

---

## Scope

This standard applies to outputs generated by AI for:

- Documentation
- Templates
- Checklists
- Prompt responses
- Knowledge summaries
- Requirement analysis
- Business rules
- Risk analysis
- Test scenarios
- Test cases
- Regression analysis
- Bug reports
- Workflow artifacts

---

## Output Principles

Every output SHOULD be:

- **Accurate** — Correct and factually consistent.
- **Complete** — Covers all requested information.
- **Clear** — Easy to understand and follow.
- **Consistent** — Follows repository standards.
- **Actionable** — Ready for immediate use whenever possible.
- **Traceable** — Material derived content can be connected to authoritative input when the artifact contract requires it.
- **Reviewable** — A human QA reviewer can scan, compare, and assess the output efficiently.

---

## General Requirements

AI outputs MUST:

- Follow the requested format and applicable canonical template.
- Use professional English unless otherwise specified.
- Avoid unnecessary explanations.
- Maintain consistent terminology.
- Preserve technical and business accuracy.
- Keep unsupported or clarification-dependent behavior visibly separate from confirmed behavior.
- Reconcile any reported aggregate counts with the actual generated identifiers/rows before delivery.

AI outputs SHOULD:

- Be concise.
- Be logically organized.
- Minimize repetition.
- Prioritize readability and scanability.

---

## Output Structure

Unless otherwise requested, outputs SHOULD use a hybrid structure:

1. Title and document-level context where applicable.
2. Canonical core artifact representation.
3. Supporting assumptions, dependencies, open questions, coverage, or summary sections where applicable.

Additional sections MAY be included when they improve clarity without duplicating the canonical core artifact inventory.

---

## Table-Oriented Core Artifacts

Artifacts that represent a collection of comparable QA records MUST use the canonical table-oriented core defined by their shared template.

The following artifacts use table-oriented core output by default:

| Artifact | Canonical Template | Core Representation |
|---|---|---|
| Business Rules | `shared/templates/Business-Rule.md` | Rule inventory table |
| Risk Analysis | `shared/templates/Risk-Analysis.md` | Risk register table |
| Test Scenarios | `shared/templates/Scenario.md` | Scenario inventory table |
| Test Cases | `shared/templates/TestCase.md` | Executable testcase table |
| Regression Analysis | `shared/templates/Regression.md` | Regression-impact table |

Document-level narrative may surround these tables, but it MUST NOT replace the canonical core table when the artifact is generated for normal QA use.

Requirement Analysis, Bug Report, Knowledge Article, and other artifacts may remain primarily section-based unless their applicable template specifies a table for a structured subset.

---

## Table Formatting Rules

For canonical QA artifact tables:

- Keep one primary record/objective per row whenever practical.
- Use stable identifiers when the artifact contract defines them.
- Keep traceability visible in dedicated columns where applicable.
- Use concise cell content; move large shared context to surrounding sections rather than repeating it in every row.
- Use `<br>` for multiple short lines inside a Markdown table cell.
- For ordered test steps, use numbered text separated by `<br>` in a single cell.
- Do not use nested Markdown tables inside a core artifact row.
- Do not hide unresolved expected behavior inside an executable row as if confirmed.
- Keep column meaning stable across examples, golden outputs, workflows, and platform adapters.

A platform/export adapter MAY transform the presentation format, but it MUST preserve the semantic fields and traceability defined by the canonical template.

---

## Aggregate Count Integrity

Whenever an artifact reports counts, totals, percentages, ranges, or category summaries derived from generated records, those values are **derived data** and MUST be validated against the actual artifact content before delivery.

Mandatory rules:

1. Count unique canonical IDs/rows, not prose mentions.
2. Category subtotals MUST reconcile to the stated total when the categories are presented as exhaustive.
3. If categories overlap, explicitly label them as overlapping and do not present their sum as a unique total.
4. Range statements such as `TC-001–TC-020` MUST match the IDs that actually exist; do not assume ranges are continuous unless verified.
5. Regression tier counts MUST equal the number of unique selected testcase/scenario IDs in that tier.
6. Coverage-status counts MUST match the actual reviewed items classified under those statuses.
7. If an artifact distinguishes register rows from additional blocked/open dependencies, label and count them separately rather than combining unlike objects into one ambiguous total.
8. Percentages MUST use the reconciled numerator and denominator shown or defined in the artifact.
9. A count mismatch is a validation failure; correct the summary or the underlying inventory before marking self-review PASS.

When deterministic tooling is available, prefer computed counts. When generation is model-driven, explicitly perform an ID/row reconciliation pass during self-review.

---

## Formatting

Outputs SHOULD follow repository documentation standards.

Use:

- Headings for document-level sections.
- Lists for grouped contextual information.
- Tables for structured record collections.
- Code blocks for examples, commands, or configurations.

Avoid excessive formatting or repeated per-record subsections when the same information is already represented clearly in a canonical table.

---

## Completeness

An output SHOULD satisfy the original request without requiring unnecessary follow-up.

When information is unavailable, ambiguous, or clarification-dependent, the output SHOULD clearly indicate it and avoid unsupported assumptions.

---

## Consistency

Outputs MUST:

- Follow repository terminology.
- Use consistent naming conventions.
- Align with related repository standards/templates.
- Avoid contradictory statements.
- Preserve the same canonical columns for equivalent artifacts unless an explicitly defined export profile applies.
- Keep summary counts, record IDs, traceability references, and stated coverage internally consistent.

---

## Reusability

Outputs SHOULD be written so they can be:

- Copied directly into repository documents.
- Reviewed by Manual QC without major reformatting.
- Exported to spreadsheets or test-management tools with predictable field mapping.
- Reused as workflow inputs.
- Extended without major restructuring.

Avoid content that is overly specific unless explicitly requested or source-grounded.

---

## Examples

Examples SHOULD:

- Demonstrate the expected canonical format.
- Be concise enough to scan.
- Reflect repository templates and field semantics.
- Preserve authoritative behavior and uncertainty boundaries.
- Use reconciled counts when totals or category summaries are shown.

Examples SHOULD NOT replace the actual requested output or introduce alternate artifact schemas without an explicit reason.

---

## Error Handling

If requested information is incomplete or ambiguous, the output SHOULD:

- Clearly identify missing information.
- Avoid unsupported assumptions.
- Keep clarification-dependent behavior separate from confirmed expected behavior.
- Continue only where authoritative/supported information is sufficient.

If an assumption is intentionally used for a non-authoritative example, it SHOULD be explicitly labeled.

---

## Quality Checklist

Before considering an output complete, verify that it:

- Follows the requested and canonical format.
- Uses the applicable core artifact table when required.
- Covers all supported requested content.
- Uses consistent terminology and IDs.
- Preserves traceability and uncertainty boundaries.
- Contains no unnecessary repeated per-record sections.
- Reconciles every reported count/total/category summary against actual canonical IDs/rows.
- Is grammatically clear.
- Can be reused/exported with minimal modification.

---

## Best Practices

- Prioritize usefulness over verbosity.
- Prefer direct and unambiguous language.
- Prefer one scanable canonical table over repeated record-by-record sections for list-oriented QA artifacts.
- Keep shared context outside rows when it applies broadly.
- Produce outputs that require minimal post-editing.
- Keep formatting consistent across templates, skills, workflows, examples, and golden outputs.
